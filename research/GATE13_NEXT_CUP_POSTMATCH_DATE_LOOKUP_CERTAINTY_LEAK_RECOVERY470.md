## Native original NEXT lookup contract

Original `PBg::0x4321E4..0x43220C` obtains **current manager+0x5B4**, its selected calendar via `0x4079D0`, and calls `0x615D10` with original date `0x9847FC`. Original `0x615D10→0x615C50` traverses source Event nodes and, for its literal NEXT arguments, must reject **existing Event+0x08 wrapper links**, payload status `+0x44 & 0x61 != 0`, unmatched source reference selectors, and a candidate that becomes linked during `0x514520` Side resolution. It returns a **source Event** only after rechecking these gates. Original `0x615DA0` used by PBg header refresh is related but may reschedule events and is **not** the same as a passive date lookup.

This audit does not reclassify the original flags as named football statuses. All source semantics here rely on the earlier independently hash-verified instruction receipts; last-mile live original outcomes and every original eligible wrapper producer are still unresolved.

## New concrete code-to-gameplay path

1. `PrimaryScheduleShadowState.next_match_date()` at `reconstruction/primary_schedule_shadow.py:336–365` iterates date buckets strictly later than `after_date`, uses `resolve_ref(ref)` or `candidate_sets` to decide participant membership, and returns **only a calendar date**. It never reads `entry.wrapper_link_state`, payload `+0x44` status (absent from `PrimaryScheduleShadowEntry`), a concrete source Event/Side identity, a result/completed flag or post-callback Event linkage.
2. This is **not only a dormant prospective adapter**: `GameState.next_primary_match_date_for_club()` at `reconstruction/game_state.py:3479–3490` directly invokes it, claiming `exact next primary-container match date when resolvable`; `_preflight_domestic_cup_post_match_dates()` at lines3492–3520 consults it **for both Cup participants** and catches *only* `PrimaryScheduleResolutionPending` (the unresolved candidate-set case). When the first matching reference resolves to a club, it does not distinguish `clear`, `linked`, or `unknown` wrapper states.
3. The normal shared Cup post-match consumer in `GameState` at approximately `3634–3720` calls that preflight, and on `exact=True` invokes `persist_premier_league_match_incidents` for both clubs (source `0x5127A0` flow) followed by morale/Form/transfer-request updates, all with shared runtime RNG. Other independent post-match mutations (condition, appearances, pitch) intentionally continue outside this `exact` gate.
4. `PrimaryScheduleShadowState.invalidate_unmodelled_wrapper_links()` at lines269–285 converts **all non-linked future events** to `unknown` after original-bounded day advancement; `restore` defaults legacy records missing wrapper state to `unknown` at lines445–450. So `unknown` is a real supported reconstruction state, not a hypothetical invalid enum. Because the cup preflight ignores it, a fully resolved **club** can cause a *wrapper-uncertain* date to be reported as `exact`.
5. Existing `test_primary_schedule.py::test_header_selector_skips_linked_but_fails_closed_on_unknown` around lines273–324 exercises a **different method**, `direct_fixed_league_header_candidate`, correctly skipping known linked and refusing unknown. The date-level tests around lines400–556 cover symbolic candidate-set uncertainty and dynamic replay insertion, but **no checked `next_match_date` test varies wrapper-link certainty**. That omission explains why this particular trust-boundary leak is not covered by the cited suite.

### Directly inspectable counterexample (not executed)

Take one manager club1, `after_date=2000-07-02`, a source-direct club1 match `A` at `2000-07-03`, and another source-direct club1 match `B` at `2000-07-04` with original eligibility otherwise normal. Put `A.wrapper_link_state='linked'` and `B.wrapper_link_state='clear'`.

- `shadow.next_match_date(1, after_date, lambda ref: ref.direct_club_id)` returns **2000-07-03** because its first matching club reference makes it return immediately; source original `0x615C50` cannot return that existing linked `A` event. Under the additional source-side conditions assumed for this bounded example, the first eligible event is `B`.
- Change `A.wrapper_link_state` to **`unknown`**, leaving its participant directly known: the helper still returns **2000-07-03** as *exact*. The correct original target is **not proven** by the retained shadow; an exact-date claim is invalid regardless of whether original dynamic processing would ultimately pick A, B or an unmaterialized wrapper.
- Both cases flow into `_preflight_domestic_cup_post_match_dates` as a completed exact result when the opposing club also resolves. This can permit incident/morale RNG work on a date not source-qualified. A different manager's correct date cannot repair the first side's certainty leak.

**Classification:** CONFIRMED code-level source-vs-date-helper eligibility mismatch and CONFIRMED downstream Cup consumer/preflight route; **conditional** effect on actual Cup post-match RNG/players when linked or unknown matching candidates occur. No specific save-game corruption, wrong injury, observed regression, or Windows occurrence is claimed without executing the representative fixture. Note that `next_match_date` was originally intentionally scoped as a *date-level* startup helper; the error is treating it as an **exact qualified live event date in the Cup incident consumer**. Do not label the entire helper or the conservative header selector universally wrong.
