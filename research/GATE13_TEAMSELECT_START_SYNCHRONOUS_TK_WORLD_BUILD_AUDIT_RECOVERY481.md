Therefore moving Squad asset loading off Tk does **not** make full startup simulation run off Tk. The existing `test_original_game_host.py::test_teamselect_start_defers_only_fresh_squad_resources_off_tk_thread` (lines~905–958) correctly tests this **art-only** thread boundary using a fake backend and `DeferredThread`, not slow canonical world-building responsiveness.

It verifies correct **work allocation**, not execution on a worker or the heartbeat of an actual Windows11 Tk event loop.

**Confirmed defect/limit:** when real canonical catalog verification/parsing or fresh world/schedule construction consumes noticeable wall time, Tk input processing cannot service its normal event loop **during that synchronous callback**. The callback's responsiveness is structurally blocked until work returns. No specific number of seconds, Windows hang message, incorrect original game loading screen, invalid RNG, or observed user failure is claimed without timing a native Windows installation. This is separate from ongoing 9–15s NEXT turn costs already delegated to a worker and the fixed 61.936s intro movie startup reported in the prior WPF audit.
