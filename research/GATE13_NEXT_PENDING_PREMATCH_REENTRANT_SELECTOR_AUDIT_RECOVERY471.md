## Exact newly live code sequence

1. Codex host `OriginalGameTkHost.on_click` (~lines2351–2410) accepts management `native_next_press` when Back5 rectangle/flags pass and PMenu/PMatchInfo are inactive; calls `_begin_original_management_turn` unconditionally with respect to `gameplay.pending_primary_entry`.

Host `_begin_original_management_turn` (~1206–1240) protects against *concurrent* worker clicks, shallow-copies the current gameplay controller and launches `staged.advance_original_management()` on a worker. `_poll_original_management_turn` (~1240–1265) publishes the new controller state, resets input-busy/flags and redraws. 3. **The new backend public `HumanGameplayController.advance_original_management` (~line1637) does NOT first test `pending_primary_entry`.** It deep-copies the controller, then invokes `staged.state.primary_schedule_shadow.ordinary_next_candidate(` with source Side resolver, native postponement callback and priority, builds a target and calls `staged._advance_original_management_turn(target)`; on success it publishes the staged `__dict__`.
4. `_advance_original_management_turn` itself **does** check `pending_primary_entry` first, returning an outcome with no processed dates. That guard is **too late to protect** the *earlier mutable selector work* performed by the public method. Original `ordinary_next_candidate` may fill Side caches, select another linked terminal or use `_original_postpone_event` to insert a wrapper/move a live primary owner **before** the check. Then even a zero-date-advance return leads to public `self.__dict__.update(staged.__dict__)`.
5. The corresponding newer GUI tests `reconstruction/test_original_game_host.py` ~475–547 test first press/thread publication and **duplicate input while the worker remains in flight**, but none of those source tests covers **a second accepted press after the first worker completed with `pending_primary_entry`**. `test_original_management_turn.py::test_tomorrow_suspends_order_at_human_before_modal_choice` ~72–95 checks the **different lower-level `advance_original_management_turn` helper** directly, whose pending guard precedes mutation. That test **does not exercise** the new mutable-selector public method or the Tk host's post-pending reentry.

## Player-visible consequence and severity

The *new* ID3 connection solves the former missing-action defect, but leaves the normal host in MANAGEMENT with no original PPreMatch/pending-modal owner. When the first NEXT worker reaches a pending human fixture, its button becomes enabled again; a user can press it again. That starts another ~10-second candidate/turn worker instead of entering the authentic pre-match decision. **This reentry is directly reachable in current normal host code** (barring other still-unobserved Windows preconditions). Whether the second selector actually rewrites a fixture depends on exact pending snapshot and symbolic neighbor/Side states; **no observed specific corruption or duplicated result** is claimed.

The original source has ordered match preparation/modals/results/stack navigation, but there is no native Windows trace proving exactly what a second header click would do *while* such a modal is open. The correct interim protection is to keep the already-pending match's state stable and fail closed until the source-backed pre-match owner handles it—**not invent a new modern modal or auto-calculate the match**.

**Classification:** CONFIRMED code-level repeated accepted NEXT after pending + mutable query before guard; potential **P0 progression/input-phase correctness** and conditional event-owner mutation; original particular double-click behavior not claimed. Codex implementation owner only.
