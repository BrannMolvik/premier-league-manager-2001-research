## Recovery539 independent x86 callback-owner resolution — two distinct parent event routes

A new **original source owner trace** answers a previously unresolved portion of the parent callback:

1. PMessageRow creation at `0x471ECC` stores native vftable pointer **`0x7C266C`** into the row object, before the `0x46E680` text-child setup. Raw original .rdata confirms **vft+0x10 = `0x471B80`** (the verified first-select/reselect PMessageRow handler).
2. Original child setup `0x46E720..0x46E734` invokes the eCText vft+0x08 with arguments **child ID2** and the parent `PMessageRow` pointer. Independently decoded eCText vft `0x7BE340+0x08` is `0x64F3C0`, which writes ID to child+0x20 and **parent** to child+0x24. The ID3 and ID0 children use the same owner binder with their respective IDs.
3. Original eCText `0x5D7380..0x5D73CB` can return T+P/T+C selector AL from `0x5D75B0` and, if its hit gate, parent pointer, ID and external call flag are all accepted, calls **parent vft+0x10** with `push event_pointer; push eCText_pointer`. The first argument at the parent is the nonzero embedded child pointer.
4. Original parent `PMessageRow::0x471B80` immediately reads `[esp+4]` and branches at `0x471B8D..0x471B8F` when nonzero, **before** any native selection or modal logic. Its actual first-click and selected-row reactivation branches therefore require the **separately sourced neutral first-argument-zero event**, not simply the child T+ text-selector callback.

5. **Crucial independent second native callback:** eCText `0x5D73E0..0x5D7432` uses a different hit gate `0x64F960` and, with accepted external-event flag, parent pointer, child ID and nonzero returned T selector, dispatches **parent vft+0x20**, NOT +0x10. PMessageRow vft `0x7C266C+0x20` resolves to **`0x471C60`**. That function checks the passed embedded child `+0x20` ID: child 2 reads saved selector from **row+0x490** (ID2 eCText base row+0x37C plus +0x114); child 3 reads row+0x5C0 and a record virtual+0x34. For child 2 it calls original `0x5CF7B0`, which has **exact ASCII P `0x50` versus C `0x43` switch**:
   - P: writes output kind 1, returns descriptor+0x04 as player reference;
   - C: writes output kind 0, resolves original club association via descriptor+0/+0x04/+0x08 and possibly DBRClub+0x24 for one subtype.
6. The same `0x471C60` then dispatches according to returned kind: **player** through `0x605DC0` with source player structure, **club** through `0x604900` with source club structure. Thus the original player/club special text **has a real source-bound secondary detail-navigation effect**. Its exact on-screen hit region, event flags/stack ordering, DBR association subtype, alternative outcomes and modal return are not yet fully source-qualified for the Windows host.
