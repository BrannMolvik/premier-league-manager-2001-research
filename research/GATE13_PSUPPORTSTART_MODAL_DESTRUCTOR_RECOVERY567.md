## Exact modal close and ownership sequence

Original first-human click `0x4D8EF8->0x413BB0` registers human, `0x4D8F75->0x4C9CD0` creates staff types (1,2,3,4,5,13), and `0x4D8F7F->0x4DA4F0` stages the staff list and seven slots BEFORE a user interacts with the editor. During normal first human creation, all FOUR original list payload-deletion owner flags have been cleared in `0x4D8F23..0x4D8F4E`; that is distinct from clearing/deleting link nodes. `0x4DA4F0` visits slot indices 6,5,4,3,2,1,0; slot6 is null, type13 is appended to selected user+0x5C4 first, and types 5,4,3,2,1 append to +0x5B8 in descending order (not natural creation order). Each moves off selected user+0x5D0 and conditionally off global 0x875600. The staging and current/global memberships must not be re-invented by Cancel.

Native `0x4D05E0` event1 jumps to `0x4D061F`, sets modal byte `+0x1DE4=0`, requests close through `0x6539F0`, and DOES NOT call Apply. Event2 at `0x4D0606` invokes the original virtual+0x4C before setting `+0x1DE4=1`; direct original PSupportStart vtable `0x7C6DDC+0x4C=0x7C6E28` holds `0x4D0830` full staff/name Apply. Original `0x450BB0` waits for the modal host, copies byte `+0x1DE4` into BL at `0x450CBF`, then invokes **native `0x5EB920` disposal** at `0x450CCD`. Thus the captured modal result survives teardown.

Original `0x5EB920` at `0x5EBA9A..0x5EBAA0` calls window object's virtual destructor +0 with delete flag1. The actual original PSupportStart vtable `0x7C6DDC+0` points to **`0x4CF790`**, which calls `0x4CF7B0` (nondeleting teardown) and frees this modal allocation on the flag. In `0x4CF7B0`, `0x4CF936..0x4CF94B` destroys **seven 0x4C-byte row selector UI structs** from modal offset `+0x2224` through `0x66820D` with element destructor `0x4D89E0 -> 0x5D4600`; additional UI/text sprite members are torn down and base `0x6532A0` is called at `0x4CFA5A`. These are the modal UI's owned members, not its externally passed staff row pointers `+0x970/+0x974` from `0x4CF124`. No direct call from this bounded UI destructor to `0x4D0830`, `0x413DB0`, or a staff list removal is present.

**Critical outer-result distinction:** `0x4D9224` calls `0x450BB0` but `0x4D922C` **overwrites the modal return value with the prior accepted base-control result from EBX**, so nested Cancel=0 does not itself mean that the original human registered by the first click was removed. The independent original human deselect branch `0x4D90C8` explicitly calls `0x413DB0`, and is not a direct part of the normal modal destructor. However this does not prove all indirect modal-message callbacks, time queue tasks or human teardown effects beyond the bounded control flow.

## Further original source: both native modal Exit and Tick post an asynchronous Win32 message

Original event1 `0x4D061F..0x4D062A` and event2 `0x4D0606..0x4D0618` both call exactly one common source close routine `0x6539F0`. Its actual source `0x6539F4` reads the window-owner pointer at object+0x64; `0x6539F7` masks the caller event value to 16 bits; `0x6539FC..` pushes a zero payload and literal message ID **0x400 (WM_USER)**, calling wrapper `0x659650` at `0x653A04`. That wrapper reads the native HWND from owner+0x04, pushes four Win32 call arguments and invokes **original PE import thunk `0x7BD2D8`** at `0x659663`. The private original executable import directory positively names this USER32 import **`PostMessageA`**, not `SendMessageA`.

Consequently, Cancel and Apply request a **posted** window event rather than calling staff cleanup synchronously. Apply still commits staff/name first; Cancel still skips Apply. The modal host `0x532650 -> 0x654210` must process the posted WM_USER event before normal `0x450BB0` returns; the message handler and any downstream callbacks are not yet statically audited in full, so no claim of entire native modal lifecycle equivalence. Do not treat the deferred UI event as another globally queued staff deletion or as manager deselect without tracing source.

Independent original SHA-verified checks for seven more exact native instruction sites and both direct `0x6539F0` callers PASS; the reproducible original static audit now asserts these. No original game launch or Windows11 GUI verification.

**Direct caller precision:** `0x6539F0` is the **shared/general UI message-post helper**, not a PSupportStart-exclusive close implementation. A full scan of original `.text` identifies **44 syntactic direct callers**, including both PSupportStart event cases at `0x4D0618` and `0x4D062A`. The original source audit correctly requires both specific callsites to be present among 44 original users; it does not assert exclusive ownership of the helper. The posted message's recipient/dispatch is a general native UI system requiring a separate handler audit.

## Recovery567 follow-up: MyWindow original event pump consumes WM_USER, not a dispatched callback

The original posted event path is now source-closed through the **original MyWindow event pump**. Original PE RTTI class `.?AVMyWindow@@` vtable `0x7CB294` has vft+0 `0x532B80`. Modal host `0x450BB0` passes original global `MyWindow` owner `0x877960` to `0x532650` at `0x450CBA`; the latter calls `0x654210` at `0x53266D`. There `0x654258..0x65425C` calls this event pump via native virtual+0.

Original MyWindow `0x532B80` sets up a real USER32 message loop with imported `PeekMessageA`, `GetMessageA`, `TranslateMessage` and `DispatchMessageA` functions (PE IATs `0x7BD29C, 0x7BD2A0, 0x7BD2A4, 0x7BD2AC`). It tests fetched `MSG.message` against **`0x400` at `0x532BBF`**; an equal WM_USER jumps at `0x532BC7` directly to `0x532BF9`, skipping normal `TranslateMessage` and `DispatchMessageA`. The handler returns `MSG.wParam` from `[esp+0x18]` (not `+0x1DE4` and not a staff result). Both native source actions `0x4D060D` and `0x4D061F` push literal **0** into `0x6539F0`, which in turn posts `PostMessageA(hwnd,0x400,wParam=0,lParam=0)`. Thus **both** Cancel and Apply terminate the modal MyWindow message pump with result **0**, even though the original modal object's `+0x1DE4` byte differs between Cancel(0) and Apply(1). Native `0x450CBF` reads that stored byte separately before modal destruction; outer `0x4D922C` uses a third, earlier accepted-control result. These three results MUST NOT be conflated.

This closes the **specific posted WM_USER message consumption path**: its WM_USER 0x400 is *intercepted by the loop*, not routed through `DispatchMessageA` or a hidden secondary staff-deletion handler. Other **previous** GUI messages and virtual callbacks may still affect user/staff state; cannot generalize no side effects. This is original SHA-verified static x86 proof, not a live native Win32 trace.

To prevent future integration bugs, `SourceOriginalSupportStartModalDispatch` now exposes `source_posted_close_message=(0x400,0)` and `source_window_loop_return=0` only after source-qualified event1/event2, distinct from native modal result byte and outer TeamSelect handler result. Unit tests cover identical WM_USER values on Apply and Cancel and no fabricated message when the original modal is not opened. Updated reproducible static audit asserts fourteen original instructions, MyWindow RTTI and native vtable pointer, and private source checks pass. Original EXE never launched and no Windows11 GUI or exact-branch CI accepted.

## Recovery567 follow-up: deselect is a distinct native registered-user deletion

Original `TeamSelect` source `0x4D90B0..0x4D90C8` performs an entirely different lifecycle transition than SupportStart Exit(event1): it passes the selected club identity to `0x413B80` at `0x4D90B6` and gets back the **zero-based index of the matching registered human** in the original users linked list `0x874C10+0x9CC`, or `-1` if not found. It writes that index into global `0x8755D4` at `0x4D90C2` and invokes `0x413DB0` at `0x4D90C8`.

Native `0x413DB0` walks registered linked-list nodes by that index, then `0x413DF6 -> 0x414680` unlinks the selected node from user owner list `+0x9C8`. Crucially, `0x414680` first calls node unlink helper `0x42CBF0`, then consults original list payload-deletion owner flag at `[esi]`: **only when that owner flag is nonzero** does it invoke user payload destructor `0x424FC0` and free the user object. In either case it frees the 0xC-byte list node at `0x4146AD`. Source `0x413E00..0x413E0D` decrements registered user count `+0x9D4` and updates current selected index `+0x9C4`. Hence an accurate port cannot simply set selected club IDs to empty and claim the native user's object/list teardown or original callback consequences have been modeled; it must respect the owner flag and actual matching registered user.

The native destructor `0x424FC0` itself begins by setting user inactive staff list owners `+0x5B8/+0x5C4` to **1** and current staff `+0x5D0` to **0**, followed by teardown of several allocated user-owned children. Its complete transitive cleanup path is longer and is NOT a verified exact first-human rollback outcome. **No direct** path from SupportStart event1's `0x6539F0` WM_USER event or modal vft destructor `0x4CF790` to this `0x413DB0` deselect call was identified; the proven path to it is the separate TeamSelect deselection at `0x4D90C8`. None of this source evidence proves a live GUI deselect works in the port. Original EXE was statically inspected only.
