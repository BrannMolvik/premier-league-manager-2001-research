## Direct source findings

1. **Original DBRPlayer constructor, `0x417700..0x417718`:** source constructor input at stack `[esp+0x20]` is read into EAX. Native instructions store its low word to both `DBRPlayer+0x10` and **`DBRPlayer+0x72`**, while `DBRPlayer+0x74` is separately initialized to signed `-1`. Thus **at that constructor boundary**, +0x72 initially equals the supplied club word. It is not a globally immutable initial-club field or necessarily equal to the current reconstructed `club_id` later.
2. **Original EAM type-2 descriptor, `0x5CE660..0x5CE695`:** stores the native player identifier into descriptor+4, reads the live native **signed 16-bit `DBRPlayer+0x72`** from the indexed DBRPlayer array, and stores the sign-extended value in **descriptor+8**. The player-array source base is the original global at `0x875640`. The descriptor therefore **captures the association when the EAM record is constructed**. Native player-label resolver `0x5CE715..0x5CE7B8` consumes the *stored* descriptor+8; it does not recompute a club association from today's mutable port player.
3. **Original producer, `0x41B61E..0x41B652`:** reads the signed `[player+0x72]`, selects the special negative/native club branch or the indexed club using the original DBRClub global at `0x874B90`, reads that club's effective manager at `+0x40`, and calls original `EAMPlayerAskTransferListsub` constructor `0x56FAD0` **at production**. This is distinct from NEXT-day `0x613EE0/0x5CFA20` delivery. The constructor's existing type-2 descriptor is the immutable association owner for later row text.
4. **Original association mutability is directly demonstrated.** `0x418E31` copies +0x10 into +0x72 during player loading. `0x41A4D0..0x41A506` saves both club words to transient +0x140/+0x142, then writes a temporarily supplied club to both; `0x41A550..0x41A57A` restores each saved word. `0x41B151..0x41B155`, `0x41C032..0x41C036`, `0x41EF73..0x41EF77`, `0x421668..0x42166C` and `0x422F8A..0x422F8E` are additional writes; `0x494269..0x4942D9` temporarily replaces +0x72 then restores its previous value. These source-controlled transitions disprove a blanket invariant `native_association_72 == port_player.club_id` for the entire career. Caller/phase-specific side effects beyond the bounded instructions remain to be adjudicated.
5. **Positive club branch, `0x5CE735..0x5CE782`:** when descriptor+8 is nonnegative, original code indexes native clubs at stride **680 bytes** (`85 * 8`), calls `0x40DA70` on the selected club, obtains another runtime-owned string from global `0x9844D8`, and formats exact original text template `<T+P>%s<T-> @ <T+C>%s %s<T->` at `0x833318`. `0x40DA70` first calls `0x403600` for a dynamic source string and otherwise dereferences club+0x0C's source string pointer. The second runtime string and exact port-owner mapping remain **UNVERIFIED**. For negative association, the separate exact literal at `0x83330C` remains `<T+P>%s<T->`. Original CP1252 first-initial/surname logic has already been preserved by PR #617.
