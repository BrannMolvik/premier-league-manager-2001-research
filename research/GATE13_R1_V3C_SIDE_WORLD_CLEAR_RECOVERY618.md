## Queue classification correction: original 0x613EC0 is NOT calendar insertion

Static reinspection of the same source **0x419648..0x41966D → 0x613EC0..0x613EDF → 0x617D70..0x617DA5**, canonically SHA-matched source:

1. Native 0x419648 constructs a 0xC-byte event record (original +0 event vtable **0x7BD564**, +4 global date 0x9847FC, +8 the separately reached event-result pointer). It ORs 0x06 into the *referenced original owner+8*, then calls 0x613EC0 with the event pointer (which may be null on prior failed allocation).
2. **0x613EC0** allocates its own **second 0xC-byte wrapper node** through 0x668140, places the event pointer in wrapper+0, then calls 0x617D70 on collection **0x947AA8**; it does not call the distinct 0x615A60 date-calendars insertion. The two 0xC allocations (event and wrapper) have separate ownership/lifetimes. Native does not locally guard the wrapper allocation EAX before dereferencing. A compatibility port should fail closed safely instead of inventing a successful allocation if the equivalent resource is exhausted.
3. **0x617D70** checks owner+8 (tail). When tail exists, stores new pointer into old tail+4, zeros new+4, sets new+8 to old tail, and sets owner+8 to new. On empty, sets owner+4 **and** owner+8 to new, and zeros new+4/new+8. This is a **doubly-linked FIFO insertion with first=collection+4 and last=collection+8**, not the calendar v18 node world at 0x947AD8/0x947AF0 and not evidence that an Inbox item has been delivered.
4. A separate **0x613EE0** routine iterates owner+4 linked nodes; the reached native event object's vtable+0x10 callback is invoked conditionally and a 0x4EA190 erase may follow. Full event subtype/recipient/effect and delivery state are still unproven. The event producer source route is therefore: native player progress → construct event → queue wrapper → pending queue → event virtual callback/delivery decision, not direct delivery.
