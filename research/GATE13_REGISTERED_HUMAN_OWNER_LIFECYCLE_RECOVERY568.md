## Original direct instruction evidence and lifecycle

Native `0x412CD0` initializes process-global `0x874C10`. At `0x412D04` it writes literal **1** to its registered-human list payload-ownership flag **`+0x9C8`**, and at `0x412D0E` clears the linked-list head `+0x9CC`. The native registered-human count `+0x9D4` and current selection index `+0x9C4` both initialize to **0** at `0x412D94` and `0x412D9A`. This is genuine source initialization, not inferred from a GUI.

Normal TeamSelect club selection `0x4D8EF8 -> 0x413BB0` first scans existing linked nodes for the SAME original club object; if already present it returns 0 without creating another DBRUser. Otherwise it allocates an original 0x10F0-byte user at `0x413BEF`, appends the new pointer in its 0xC-byte node to `+0x9C8` via `0x413C44/0x413C4A -> 0x617D70`, initializes the user/name/manager, then at `0x413C60..0x413C71` sets current index to the PREVIOUS registered count and increments count. This is distinct from staff staging and the SupportStart modal.

Original TeamSelect **deselection** at `0x4D90AD..0x4D90C8` identifies the selected existing original club record then invokes `0x413B80` to find the corresponding user's linked-list index and `0x413DB0` to unlink it. Native `0x413DFB -> 0x414680` first invokes unlink helper `0x42CBF0`. Source `0x414692` tests **the list owner's payload-deletion flag**, not the staff selector flag or SupportStart Apply result. If it is nonzero, `0x41469F` invokes **`0x424FC0` the original user payload destructor**, then `0x4146A5` frees that user payload allocation. The 0xC-byte list node itself is freed at `0x4146AE` **regardless** of the owner flag. Source `0x413E00..0x413E0D` decrements human count and sets current index to **count-1**, including **-1 after removing the last human**, even though fresh constructor initializes current index to 0. Original destructor `0x424FC0` sets user staff list payload owner flags `+0x5B8,+0x5C4` to 1 and `+0x5D0` to 0 before its deeper teardown (see Recovery567). The exact transitive staff/global and event queue effects remain unverified.

This closes the **bounded fresh-world owner-flag ambiguity**: the native new-game registered-user owner is initially payload-owning=1. It does not prove all alternative saved worlds, indirect setters or later callback effects retain that value, nor does it make SupportStart Cancel a deselection. `0x413B80` assumes a real matching club pointer; the reconstruction fails closed when caller supplies a missing club rather than inventing an impossible removal.

## Recovery569 correctness correction: native parent row may accept without either input child

**This corrects the overly narrow Recovery568 wording above.** While the registration flags indeed permit **only child3/child4** (of five) to participate in the child-input subloop, those children are **NOT a necessary condition for an accepted row event**. Original row parent vtable `0x7C6780+0x6C` points to `0x5D6270`. That native method first calls `0x5D4790` at `0x5D6280`, then toggles its row bit15 via vft+0x98 only if the aggregator returns nonzero. Actual full source flow of `0x5D4790`:

1. At `0x5D479B`, the **second native event argument** is tested. If non-null, the parent itself runs source `0x64F7A0` at `0x5D47A5` **BEFORE all children**. The parent result is stored in EBP at `0x5D47AA`. A parent failure immediately returns zero at `0x5D47B0`, skipping even otherwise eligible children. A parent success enters the children loop with accumulator **1**.
2. When the second argument is null, parent dispatch is bypassed and child accumulator initializes **0**; children may still be invoked. Each registered child with flags bit0x04 and its own enabled control bit0 then has vft+0x6C called at `0x5D47E8`. `0x5D47EB` bitwise-ORs each child result into the accumulator. The final `0x5D47F6` returns **parent OR any accepted child**. A successful parent is enough for bit15 toggle even if neither child is eligible or accepts. If no second argument, an accepted child may be sufficient.
3. The shared source control gate `0x64F7A0` checks state bit1 set and bit0x10 unset (`0x64F7AC`, `0x64F7B8`) before optional hit-owner `[esi+0x24]` vft+0x0C at `0x64F7DA`. Only an actual passed native event/hit context or observed return can qualify a physical mouse click. Passing base control flags alone does not qualify pixel hit acceptance.

The prior statement **"only the final two child controls are eligible"** remains true strictly for the CHILD LOOP, but **not** for whole-row acceptance. Original source `0x64F300` initializes control+0x18 to `0x183`, so a normal fresh parent has bit1 set and bit4 clear; subject to the optional original callback/hit context, a non-null-event parent can accept even when child3/child4 do not. A blank row's refresh clears parent bit1 and both child bit1, so it still cannot qualify native input through the source base gate.

**Implementation:** `reconstruction/original_supportstart_input.py` now has a bounded `project_original_supportstart_row_native_dispatch` requiring explicit native second-argument presence and source-observed parent/child Boolean results. It models the parent-first rejection short circuit, optional parent success, actual invoked child indices, and final Boolean OR without inventing coordinates or side effects. It is suitable only for already-observed source callbacks. Five focused regression methods test parent-only acceptance, early rejection, child acceptance without event argument2, disabled blank row, and invalid observations. ## Recovery569 source press-state correction: native 0x64F7A0 accepted control sets bit0x10

Further private static x86 tracing identifies a required state transition **before** the original seven-row bit15 toggle. On a successful input, source `0x64F801..0x64F807` invokes accepted control's virtual **+0x1C(1)**. The original PSupportStart row parent vtable `0x7C6780` and both input-eligible child3/4 vtables `0x7BE530`, `0x7BFF14` all point vft+0x1C to **`0x64F470`**. With the argument1, `0x64F470` invokes `0x64F710` with mask **0x10**, and `0x64F720/0x64F722` ORs that mask into the control's state DWORD at +0x18 if not already set. The original row aggregator's successful result then reaches **`0x5D6270 -> vft+0x98`** and flips parent bit15 (and first three child bit15 flags), leaving bit0x10 in any accepted event control. A subsequent generic input with that bit0x10 still set will fail native `0x64F7B8` pre-gate until the separate source `0x64F860 -> vft+0x1C(0) -> 0x64F750` clears it. **Do not fabricate a release event/clock time**.

The source dispatch projection now also returns `source_post_virtual_gate_row` reflecting only the direct bit0x10 on accepted control(s), and `source_after_row_bit15_toggle` for the subsequent true native row virtual+0x98 effect. Opaque callbacks may still mutate more fields; these remain outside the projection. ## Recovery569 input callback binding and repeated-press correctness

Source `0x64F3C0` sets a control's callback flag/owner at **+0x20** from its first argument and callback interface pointer at **+0x24** from its second argument (`0x64F3C8,0x64F3CB`). The real PSupportStart row parent vtable `0x7C6780+0x08` points to **`0x5D48C0`**; at `0x5D48D0` this first registers those callback parameters on the row parent itself through `0x64F3C0`, then at `0x5D48E8` calls **each of its five child virtual+0x08** setter functions with the same input callback pair. Source actual vtable +0x08 on **all five** child classes `0x7BE9BC,0x7C66C8,0x7C66C8,0x7BE530,0x7BFF14` is **`0x64F3C0`**. This establishes that visual child registration input flags and actual callback binding are separate mechanisms, and all child controls receive the same callback interface even though only the final two registrations have child-event bit0x04.

In accepted-event routine `0x64F7A0`, source `0x64F7C0` checks whether +0x20 is nonzero and source `0x64F7CF` whether the second native event arg exists. Only if **both** do so does `0x64F7D3` fetch +0x24 and invoke the **opaque interface vft+0x0C** at `0x64F7DA`, passing the native control and event value. Callback return0 aborts the acceptance path at `0x64F7DF`. When there is no callback binding or no event argument2, this optional vft dispatch is bypassed; base control flags can suffice for a generic accepted native event, but that does NOT prove a real mouse coordinate hit. The concrete +0x24 callback implementation, input argument layout, and rectangle coordinate transformation remain **unresolved**. No row-wide geometry or mouse automation should be inferred merely from +0x08 setter ownership.

Also, once accepted input sets source control state bit0x10, `0x64F7B8` blocks a second accepted press on that control until the separate native release vft+0x1C(0) actually clears the bit. A new focused regression test checks that a repeated source parent acceptance with bit0x10 set fails closed, while an explicit rejected observed callback returns no row event. No arbitrary synthetic release timing was inserted.

**Verification:** independently checked **10 original x86 instruction addresses and five actual +0x08 source vtable slots** against the SHA256-verified private executable.
