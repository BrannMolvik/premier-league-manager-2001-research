## Whole normal match journey and actual owner

The latest main `6612a267` retains conditional normal management NEXT and the original `0x513010` route. Native `0x513031` sets `esi` to the *LeagueMatch processing object*. At `0x513074–0x51307C`, `edi = esi + 0x14` captures the **embedded first-side subobject** and invokes its virtual+0 club getter. An unrelated second-side subobject is at processing object `+0x28`. Both sides may influence earlier human-match flag `+0x44 bit 0x10` through `0x4037B0` (`0x51307E–0x5130A4`). The `0x5130C2` v+0x34 result and reached `0x516080` remain earlier routing predicates.

At `0x513238`, if processing object `+0x44 bit 0x20` is set, the native routine **skips the first-side getter and `0x5DA2F0` entirely** to `0x513294`. Otherwise `0x513244–0x513252` calls `edi`'s virtual+0 again (its return is the first-side club pointer) and passes it as `ECX` to native `0x5DA2F0`. It separately passes `esi` (match processing object) on the stack. Consequently `0x5DA301: mov esi, ecx` inside that callee refers to the **club/first-side object**, not outer processing `esi`. `0x5DA2FC` receives the separate processing-object stack argument and `0x5DA303–0x5DA30C` fetches that object's second side through `+0x28` into `edi`. Any adapter that reads all later `+0x124/+0x144/+0x148` offsets as processing-object fields would mutate the wrong owner.

## Source-matched human versus nonhuman first-side branch

Original `0x5DA31A: call 0x4037B0` branches at `0x5DA321` to `0x5DA538` when no registered human club matches. `0x4037B0` is a global `0x874C10` wrapper for `0x4139E0`; that reads original first-side **club DWORD+4** and `0x4139F0` traverses `0x874C10+0x9CC` registered user-linked nodes. Each node+0 is a user pointer, user+0x5B4 is the manager-context pointer, and context+4 is tested against the **entire DWORD** club key. On no match, nonhuman `0x5DA538` uses actual club object fields `+0x134/+0x138/+0x13C/+0x140`, with separate optional other-object probes at `0x5DA5D9`, rather than human-owned statistics.

When `0x4037B0` succeeds, `0x5DA327–0x5DA331` calls `0x403850`. That calls `0x4037B0` once again; on success it passes club DWORD+4 to `0x413B40`. **Different lookup:** `0x413B4E` masks the key with `0xFFFF` before traversing the same native registered-user list, returning the **first user with exact context+4 equal to that masked value**. Human branch `0x5DA331` dereferences selected native user+0x694 for `0x618E00` and `0x5DA34F` dereferences selected native user+0x6B0 for `0x65D920`; subsequent calculations include additional user data and FPU arithmetic. These are source pointers, **not** a fabricated user ID or proven gameplay statistic.

The two lookups are not equivalent for arbitrary native DWORD keys. Synthetic counterexample: club key `0x10042`, manager entries in linked order `[0x42, 0x10042]`. First `0x4037B0` succeeds only on the second manager, then `0x413B40` masks to `0x42` and may return the first manager. This discrepancy is directly implied by original opcodes, but **the actual game reaching such high-bit IDs remains unverified**. An isolated low16 match without a full-key match does not enter the human branch.

## Material world-write barrier after either branch

The two source paths reconverge for processing-specific work, including user-context/other-owner transforms and FPU calculations. The callee can write processing context `+0xD84,+0xD8C,+0xD90,+0xD94,+0xD98,+0xD9C` at `0x5DB71A–0x5DB7C3` before its optional first-side update stage. At `0x5DB7D0`, a reached intermediate local flag may jump directly to `0x5DB9F2` and **skip** first-side writes. Otherwise at `0x5DB7D8..0x5DB9EC`, original first-side object `+0x148,+0x160,+0x144,+0x124,+0x128,+0x12C,+0x130,+0xE8` is modified, including an iterative weighted update with divisions and clamp. These stores are not unconditional. The intermediate flag and calculation operands still require original callback/owner evidence, not source-neutral modern stats.

After native `0x5DA2F0` returns, `0x513257` **re-reads** processing object+0x44 bit 0x10 and only then selects a native mode. For modes 0/1, `0x533D80` receives variants 0/1; mode 2 uses `0x5331C0`; mode 3 calls neither modal. All reached paths still call processing object virtual+0x38 and +0x3C at `0x51329D/0x5132A9`. This first-side qualification does not replace calculation, those post callbacks, PResults event ticks, a real GUI, Save/Load, or the management return.
