## Original source identity, key producers and bounded semantics

- `League::0x4F4A10` checks `League+0x58` form-prepared cache. On cache miss it loops through source League members at `League+0x34` using count `League+0x38`; calls `0x4F4970` on each club; runs native `qsort` (`0x668DA4`) over pointer entries of width 4 with **form comparator `0x4F4A70`**; then stores `League+0x58=1` and clears League `+0x40 bit0` (the position-ranking prepared state). This is **a distinct Current Form ordering**, not `0x4F45E0` League Position.
- `0x4F4970` resets club source form accumulator `club+0x28=0`, resolves club owner through virtual entry0, gets calendar root via `0x4079D0` (which chooses `0x947AF0` or `0x947AD8` based on `0x403640`), and searches back through `0x615ED0` in a loop limited by **6** iterations. It terminates on missing matching source node. For each source node, its vtable `+0x44` yields one participating/winning club pointer or null: nonnull equal to current club increments accumulator **+3**, nonnull unequal increments **+0**, null increments **+1**. This arithmetic is directly established at `0x4F49C8..0x4F49E9`, not inferred from reconstructed results. The later `0x510A20` call advances search context between iterations.
- The original `0x615ED0` searches day indices backwards from the requested cursor minus schedule base (`0x615ED6..0x615EE3`), traverses `0x615C50`, and respects a conditional flag/path whose class+0x44 bit6 check at `0x615F11..0x615F23` can skip source nodes. Correct filtering of which recorded matches participate and primary-vs-secondary calendar lifetime requires caller/context tracing; **do not present a naive last six Premier League fixtures as proven original Current Form**.
- `0x4F4A70` compares `club+0x28` **descending** and resolves remaining ties by original club short-name **CP1252 byte comparator ascending** via club virtual owner and nested string pointer reads. It returns `0` for fully equal form/name keys; native qsort tie permutation is not source-closed. Unlike League Position comparator `0x4F45E0`, it does not compare played, goal difference, GF or GA before the short name.
- `PLeagueTables` has genuine original sort event15, and current reconstruction `original_league_tables_selector_context.py` retains this event; `original_league_tables_presenter.py` refuses to display Current Form with unproven backend rows. This fail-closed behavior remains appropriate until actual `0x4F4970` participant/competition/date/status semantics and bridge owner are implemented. Original observable source status: **SOURCE-VERIFIED for bounded form scoring/comparator/cache**, **UNVERIFIED for full selected Current Form row set, normal host mouse selection and Windows11 player acceptance**.

## Recovery520: original fixture-date cursor and two-way calendar identity

Further source disassembly of the same hash-qualified original PE **closes the exact past-date advancement rule** for `League::0x4F4970`, and independently challenges the prior calendar interpretation:

1. At `0x4F4986..0x4F49A4`, the original function reads current in-game date from `0x9847FC`, passes exact `(club-owner pointer, date cursor, selected League pointer, strict=1, status-bit5 expected=0)` to `ScheduleContainer::0x615ED0` on the schedule root selected by `0x4079D0`. `0x615ED0` uses inclusive date index `date - container+0x08`, decrementing until a qualified fixture wrapper is found or the search is exhausted. Its strict flag checks wrapper `+0x08==0` and fixture `+0x44 bit6==0` **after** `0x615C50` matches the owner/League/bit5 criteria. The generic scan and form strict scan must not be conflated.
2. On each accepted fixture, `0x4F49ED..0x4F49FC` invokes `fixture::0x510A20` with a local output slot. In `0x510A20`, it reads fixture `+0x10` (native calendar-relative day index), calls `0x510300`, adds the returned ScheduleContainer `+0x08` base and writes **absolute fixture day** into the output. `0x4F49F8..0x4F49FA` then reads that day and subtracts **one** before the next `0x615ED0` scan. Therefore the original skips any second source fixture for the same club on that same day. It scans up to **six distinct qualified historical fixture days**, not arbitrarily the last six match records on a date.
3. `0x510300` chooses secondary `0x947AF0` exactly when the **fixture's own byte `+0x0C` bit0 is set**, primary `0x947AD8` otherwise. This is separate from the lookup's initial club-owner subtype switch `0x4079D0→0x403640` (owner byte `+0x74` codes2/3 choose secondary). Consequently a lookup selected on one container whose result fixture declares a different container is a potential counterexample requiring source proof; the port cannot simply choose the container by selected competition ID.
4. Native `0x615C50` skips candidates with mismatched fixture bit5, League `+0x4C` pointer or participant virtual `+0x04`. With form caller's inner final flags zero it may return a candidate *before* wrapper and bit6 checks, which is why `0x615ED0`'s strict check is indispensable. Fixture winner at vtable `+0x44` still needs exact class/played-state linkage to the port's recorded results, particularly null-winner on unplayed or unresolved nodes.
5. The original form bytewise name comparator is directly visible at `0x4F4AAB..0x4F4AED`; do not substitute Unicode collation, `str.casefold()`, or an identifier tiebreaker. The existing recovery's full-key-equality uncertainty remains.

**Source-confirmed outcomes:** schedule selection and date arithmetic, one eligible fixture per searched day, six-iteration cap, native 3/1/0 aggregate and source CP1252 comparator. **Still unknown:** concrete club-type+0x74 source field in all human/AI/secondary contexts, eligible native fixture class/vtable+0x44 and result status, original source secondary calendar retention, original GUI mouse hit activation. These unknowns block a completed player-visible Current Form implementation. No original process or Windows11 UI test was run; no gameplay code or original assets were added to Git. ## Recovery521: original LeagueMatch RTTI and exact native Current Form winner semantics

The original `0x4F49A8..0x4F49C3` takes the returned source schedule wrapper, invokes its virtual `+0x18` to get the concrete match, then calls MSVC `__RTDynamicCast` at `0x668995` with source RTTI descriptor `0x81B3F8` (`Match`) and target `0x81B410` (`LeagueMatch`). Descriptor names `.?AVMatch@@` and `.?AVLeagueMatch@@` were independently confirmed as literal private PE data. **Current Form's result query is therefore for original LeagueMatch objects, not arbitrary cup fixtures sharing a participant.**

- The original `LeagueMatch` complete-object locator `0x7E5478` is referenced immediately before its virtual method table at `0x7C4C24` (`0x7C4C20` holds locator). The slot `+0x44` points to exact `0x513F70`. Verified pointers to nearby getters: `+0x48 → 0x513E70` and `+0x4C → 0x513E80`.
- `0x513E70` reads **signed 16-bit** left/home goals from original LeagueMatch `+0x3C`; `0x513E80` reads **signed 16-bit** right/away goals at `+0x3E`. `0x513F70` compares those values: left greater → resolves original first-side club through polymorphic ref at `LeagueMatch+0x14`; right greater → resolves original second-side club via ref at `+0x28`; equality → returns **null**. This is the concrete winner/null value consumed by `0x4F4970` in its native 3/1/0 score accumulation; no replacement result scoring rule is invented.
- **Critical counterexample:** `0x513F70` itself checks neither completion bit `LeagueMatch+0x44 bit0` nor source result persistence. A scheduled but unplayed match whose signed score words are 0/0 would return null like a *draw* through this method. It remains unresolved whether original `0x615ED0` candidate selection and current-day boundary always avoid such nodes, or whether the original routinely grants that native form point. Therefore do **not** translate `live.results.get(token) is None` into a draw or a loss, and do not silently drop every unplayed source node as if source-confirmed. Reconstruct correct original bit0/score initialization/date qualification first.
- This direct RTTI and virtual dispatch proof resolves an important source class-identity gap from Recovery520, but does **not** establish the full original Current Form eligible roster/history, season rollover, or normal mouse activation. Source-vtable metadata and C++ RTTI are kept as textual evidence only, not copied private bytes.

**Next:** original `LeagueMatch` constructor/score initialization and status-bit0 relation to `0x615ED0` form lookup, club subtype+0x74/secondary-calendar eligibility, then source-backed results-to-form adapter and complete presenter on a worker PR with original-derived negatives. ## Recovery522: original LeagueMatch constructor zero state and eligible-unplayed counterexample

Source `LeagueMatch::0x5104F0..0x510517` invokes base `Match::0x5103D0`, then installs LeagueMatch vtable `0x7C4C24` at `0x51050E`. The base constructor unambiguously writes:

- `0x5104CF`: match `+0x44` completion/filter flags **zero**, i.e., not yet marked played.
- `0x5104D2`: separate signed word at `+0x40 = -1` (do not invent its meaning).
- This is independent of the later `0x513F70` winning-side vtable method, which examines only scores and resolves clubs without a played-bit check.

**New verified conditional counterexample:** An original newly constructed LeagueMatch that remains 0–0/bit0-clear, retains both original club sides, matches original selected League, is scheduled on/before lookup date, and has wrapper+0x08==0 and source flags bit5==0/bit6==0 can qualify under `0x4F4970 → 0x615ED0 → 0x615C50`. The original query's inclusive current-date bound and nonplayed-bit absence make this technically possible, notably on a matchday before simulation, although full runtime prevalence is unobserved. This excludes both common invented substitutes: (a) counting only `live.results` matches, and (b) treating every missing result as a stored 0–0 match without a source-qualified calendar node and flags.
