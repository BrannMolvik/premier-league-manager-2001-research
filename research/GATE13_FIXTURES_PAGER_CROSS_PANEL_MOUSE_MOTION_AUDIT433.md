## New confirmed cross-panel performance regression *risk*: `_fixtures_page_controls` calls a full snapshot before deciding it is on Fixtures

Direct reconstruction call graph, not an inference from wall-time:

1. `reconstruction/original_game_host.py::_apply_management_resources` loads the later `fixtures` family and permanently assigns `self.fixtures_pager_art` from its required payload; `_management_resource_families_loaded` remembers families. Navigating subsequently to Squad or League Tables does **not** clear this decoded pager-art object.
2. `original_game_host.py::on_fixtures_pager_motion` is bound to Tk canvas `<Motion>` and unconditionally iterates `for control in self._fixtures_page_controls():` for management motion. It is **not** limited to the Fixtures panel, and no changed/hover-bit condition guards the call.
3. `_fixtures_page_controls` checks for an active match-info modal, management screen, non-null presenter, and `isinstance(self.fixtures_pager_art, OriginalFixturesPagerArt)`. **It then runs `snapshot = self.management_presenter.snapshot()` and only afterwards checks `snapshot.panel_class != 'PLeagueFixtures'` and returns empty.** Thus when Fixtures resources have been visited/imported, pointer motion on the Squad screen triggers a full *Squad* snapshot even though the Fixtures pager is absent on that screen.
4. `OriginalManagementPresenter.snapshot -> build_management_panel_snapshot -> ManagementSourceDataBridge.squad_rows` iterates all controlled-club players and evaluates current condition/form, performance average, current-role rating, original status selectors and paired first/reserve membership. On League Tables, it similarly builds the full table snapshot. This repeated data work occurs **synchronously on the GUI thread** before `_fixtures_page_controls` returns `()`.
5. The same `_fixtures_page_controls` is invoked in `_draw_fixtures_pager` on **every** management redraw, and `on_click` when checking possible fixture pager presses while the PMenu popup is closed. After Fixtures has loaded, a Squad header hover may first produce an unneeded full Squad snapshot on each motion, then schedule an animation redraw that already rebuilds a full snapshot, **then** the painter calls `_fixtures_page_controls` and rebuilds it yet again. These are separately identifiable calls; do not invent exact time or event counts without a Windows receipt.

**Classification: CONFIRMED code-level cross-panel unneeded recomputation; POSSIBLE contributor to reported menu slowdowns; no Windows measurements or original-game input/timing equivalence yet.** This is more specific than Recovery432's ordinary redraw cost because it occurs on passive mouse motion *without any change or redraw*, but only after a Fixtures pager resource has been made available. It is not proof this caused the earlier observed latency before the user visited Fixtures.
