## Native user/mail lifetimes are distinct, and may coexist across up to six managers

Original user construction `0x424E2E–0x424E4B` installs separately allocated mailbox-list header at **DBRUser+0x6B4**, with tail-appended doubly linked 12-byte nodes (`0x617D70`). `0x413020` may allocate a distinct node for each **qualified recipient**, not the currently displayed human alone. The global `0x947AA8` pending event list is separate. Original `0x613EE0` drains due events through virtual+0x10 when event+0x04 <= date and then loops **all registered managers** using user-count `0x8755E4` and `0x413B10`; on *each* user+0x6B4 it runs mailbox maintenance `0x5CF990`. The original currently selected manager is distinct from the registered manager iteration index. TeamSelect `0x413BB0/0x4DA4D0` supports **up to six simultaneously selected managers** (or source availability limit lower than six).

The class-specific `MPMEAMail` readiness `+0x3C` and recipient route occur at delivery, not on Inbox paint; source record `+0x04` receives the scheduled envelope date and `+0x40/+0x44` governs retention/cleanup, with documented original examples of **365** and **21** source date-units. None of this gives license to invent a generic daily global list or guarantee mail is saved in the original format without inspecting native save writers/readers.

## Current Codex source owns two queues and exactly one active human snapshot

- `GameState` stores `contract_renewal_suggestions` and `player_transfer_requests` as separate arrays (around game_state.py:265–275). They are **queued source-subsets**. `ManagementSourceDataBridge.message_source_queues()` (1774–1864) projects them with player/queued dates and explicitly sets `due` for transfer requests but still returns not-yet-due rows; there is no delivered `DBRUser+0x6B4` registry, append node ID, sorted user Inbox index or message-detail status. That is **intentionally fail-closed and not an existing visible message bug**.
- Modern `internal_save.snapshot_game_state` at lines1459–1482 serializes these **two independent** arrays as simple lists of player ID, queued date and kind/due date. `restore_game_state` at lines1888–1907 reconstructs those same two queue types. **There is no third serialized manager-delivered mailbox**: not a lack of a hypothetical original field name, but a directly checked current schema omission. The original `+0x6B4` node allocation/lifecycle cannot be recovered from these queue-only JSON rows after a save.
- Modern `internal_save.snapshot_human_gameplay` at lines2031–2110 serializes `controller["human"]` as exactly **one nullable object** with club, shape, formation, eleven/bench and orders; `restore_human_gameplay` at lines2113+ creates at most **one HumanManagerState** and sets one `state.user_controlled_club_id`. It does not encode a registered list of 2–6 user identities, each with its independent mailbox, or a selected manager index with the original `0x8755D4` rotation semantics.
- The front-end retains a source-shaped `selected_club_ids` tuple and maximum six at `FrontEndSession.set_club_selections` (152–185), but **START explicitly rejects `len(selected_club_ids) != 1`** at lines253–260. This is an honest one-human backend limit, not original game behavior. A single Southport run followed by a separate other-club run is **not** multi-human message ownership acceptance.

### Exact regression hole if Inbox is only added as a screen

A hypothetical naive implementation draws Inbox rows from `message_source_queues()`, lets user select a row, then saves the game. It has neither a delivered record to assign the original recipient nor a stable node/record identity to restore that chosen row, and could display a future transfer request before due delivery. Adding `PBg ID1` and `PMenu0x65` bitmaps/panel alone cannot close original Inbox; adding only in-memory `delivered_messages` without **modern internal save/restore and source event delivery timing** would lose per-user state on reload. This is a **confirmed missing serialization/owner capability** with a **conditional future user-data-loss risk**, not a claim that anyone has already saved a mailbox through a nonexistent UI.

The shipped original save-file byte format for `user+0x6B4` is **UNKNOWN in the currently cited source reports**. The clean-room internal format is a separate compatibility representation. Do not claim original-native save import/export or prescribe a guess about native node pointer addresses on disk; maintain source-equivalent *behavior* and test own internal format without conflating it with the original binary codec.
