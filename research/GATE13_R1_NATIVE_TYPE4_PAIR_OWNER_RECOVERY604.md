## Exact reached source: Type4 from 0x4F28A0 to 0x4FAF70

PR696 established that real embedded LeagueMatch SideRef virtual+0 is `0x510320`, with uncached (SideRef DWORD+4==0) delegates into `0x4F28A0`, not an unconditional club equality. Its native selector WORD+0x0C type4 dispatches `0x4F2A78`.

On native SideRef+0x08 owner, `0x4F2A7B` invokes original **0x4FAEA0** and **does not continue if AL=0**. This gate is stateful: original 0x4FAEA0 examines owner +0x3C/+0x68, may construct two pair arrays via +0x6C/+0x70, records +0x74/+0x78 and +0x7C/+0x80 and calls original `0x617500`. These arrays cannot be supplied from arbitrary symbolic modern cup fixtures or assumed stable before this gate.

When gate AL=1, `0x4F2A88..0x4F2AA4` splits SideRef WORD+0x0E into the actual original 0x4FAF70 call arguments: **flag0=selector&1**, **flag1=(selector>>1)&1**, **index=selector>>2**. Original `0x4FAF70` reads owner **+0x74 array if flag0=1**, otherwise **+0x7C**, obtains the pair at `index*8`, returns its **first** member pointer if flag1=1, otherwise its **second** member pointer. The returned object is an input SideRef; it is **NOT** yet the final resolved club pointer. Original type4 then constructs/modifies a temporary standalone SideRef with vtable 0x7C4D60, invokes its virtual+0 and writes the final return to embedded SideRef+4 at `0x4F2B2A`. Its real nested getter, mutating owner and registration effects are not yet reconstructed.

## Additional exact original 0x4FAEA0 entry gate and source lifecycle

Native `0x4FAEA6..0x4FAEBB` loads **signed League+0x3C team count**, divides it by 2 rounding toward zero, computes `half*(half-1)`, and compares it **signed against raw League+0x68 DWORD**. Source enters the arrays-ready/initialization path if **threshold >= raw+0x68**; it returns **AL=0 immediately** if threshold is less than the raw counter. For canonical 12-team Scotland the numerical threshold is `6*5=30`. The originally unresolved +0x68 lifecycle was traced further in the same recovery: original Scottish split 0x4FADE6..0x4FADEC increments League+0x68 immediately **after** each 0x615950 original event insertion (first of two match constructors); 0x4FAE5C..0x4FAE66 similarly increments after the second. The original match-results callback 0x4F4160 retains its parent owner in EBP and at 0x4F422A..0x4F4233 reads and **decrements that owner+0x68 after genuine match-side/world writes**. For these reached producer/consumer paths, +0x68 is an **outstanding scheduled-match count**, not a chronological day or rank. Do not assume its entire all-country and non-Scottish lifecycle is now proven. Original only reads +0x78 **after** passing this gate. A nonzero +0x78 skips initialization and returns AL1. A zero +0x78 after passing the gate calls the original two-side sort/array population, including `0x4F40B0` ranking and `0x617500` twice; source leaves its real world mutation unresolved. The new bounded `source_original_type4_owner_read_only_gate_4faea0` therefore returns AL0/AL1 only for **unmutated reached** branches; otherwise returns explicit initializer-required status, not a fabricated array or success.
