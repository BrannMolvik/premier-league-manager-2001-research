## Genuine nested list input owner and original hit precedence

The original popup constructs its nested list vtable `0x7BFD5C` through native 0x449300→0x446740→0x6510F0; see Recovery593/595 source report. Its actual **virtual+0x6C method is 0x6516F0** (exact original vtable DWORD independently verified). The original function calls base `0x64F7A0` with second callback argument zero, then iterates the N native row descriptors in allocation order, each exactly 0x30 bytes, and tests raw pointer coordinates in a half-open rectangle:

- x must be ≥ `[native_row+0x08]` and strictly less than `[native_row+0x10]`.
- y must be ≥ `[native_row+0x0C]` and strictly less than `[native_row+0x14]`.
- On the **first matching** descriptor only, original 0x65174A invokes that native row object's **virtual+0x6C** with the original pointer and second input argument and immediately returns. The row's original vtable `0x7D8118` virtual+0x6C is `0x650F00`. If none match, source returns EAX0. Overlapping descriptors prefer first, not last. x==right or y==bottom is outside.

## The important distinction: hit does not automatically mean selection

At original row virtual+0x6C `0x650F00`, disassembly first calls generic 0x650C30; separately it checks child+0x2C rich option pointer, parent-owner option enable bit (`[option+0x64]->+0x48 & 0x10`), and pointer x/y against a second row content rectangle. On passing it invokes native 0x651660 with the existing `option+0x68` source index. However original `0x651660` forwards native item vft+0x10 callbacks with **both explicit callback arguments zero**. The rich option vft+0x10 `0x653A10` requires a NONZERO callback argument before posting actual WM_USER selected index. Therefore this path does **not by itself** prove a click committed a dropdown selection; likely additional pointer event gating/dispatch is elsewhere. ## Recovery595 correction: registered native rich-option child closes conditional pointer-to-selection source graph

Static follow-up of the same authenticated original source RESOLVED the apparent gap between 0x651660's zero-argument reset callbacks and the original nonzero row activation. Original rich row content factory 0x449470 installs vtable 0x7C0334 and invokes its virtual+4 setup `0x4491A0` during item construction. That sets item+0x3C **ONE interactive child**, stores pointer to **item+0x13C** (derived vtable 0x7BE340) in item+0x20, invokes nested child virtual+8 (`0x64F3C0`) at `0x4492AC..0x4492B1` with event argument **1** and parent pointer=item. Thus native child+0x20 registered event=1 and child+0x24 parent=rich item. Native child constructor `0x64F300` sets DWORD+0x18 initial flags 0x183 (input bit1 active; bit4 clear). The other native child at item+0x10C is initialized with event0 and is NOT the source of this registered-click callback.

Original row input vft+0x6C 0x650F00 first forwards to 0x650C30. If row+0x2C rich item exists, `0x650C30` calls `0x653480` on it, which normalizes original pointer x/y by rich item+0x0C/+0x10, loops its registered child controls in item+0x20, requires child input flags+0x18 BIT0 and a child half-open rectangle `[+8,+0x10) × [+0x0C,+0x14)`, then calls that native child vft+0x6C with **second argument 1** (exact 0x6534E7). Its installed 0x7BE340+0x6C = 0x64F7A0. Native base 0x64F7A0 accepts only bit1 active/bit4 clear, registered event+0x20 nonzero and the callback arg1 nonzero. It invokes parent vft+0x0C (for rich item 0x7C0334+0x0C = **0x42DE00**, which returns EAX1), followed by parent vft+0x10 = **0x653A10**. This is the genuine nonzero activation source missed by treating 0x651660's zero-argument *separate* callback as the final mouse path. `0x653A10` posts the original selected-item WORD via WM_USER to modal 0x532B80 as proven by merged PR670/671.
